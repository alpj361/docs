## De labels a claves estables

La migración v4 introdujo:

- `field_keys` y `preset_keys` en `codex_universe_items`;
- `codex_user_fields` y `codex_user_presets`;
- claves `sys_...` y `usr_...`;
- validación estricta REST y MCP;
- eliminación de la propiedad global `flag`;
- espectros mediante campos `eje`.

Resultado inicial del 25 de agosto de 2026:

| Métrica | Resultado |
| --- | --: |
| Ítems conservados | 1,329 |
| Valores `flag` eliminados | 206 |
| Ítems con `field_keys` | 620 |
| Asociaciones campo–ítem | 1,443 |
| Cambios pendientes en el segundo dry run | 0 |

El campo histórico `Oficina` de Actor se registró como `usr_oficina`. Los valores `flag` no se transformaron en ejes porque no existía una correspondencia semántica segura.

## Cambios v4.1

- `Source` se convirtió en el octavo ítem oficial.
- `Fuente` ahora se normaliza a `Source`, no a `Objeto`.
- `Post` y `Snippet` se clasifican como auxiliares.
- `Actor.is_profile` distingue Perfiles de personas reales.
- `Simulacion` se publica como recurso separado.
- Las simulaciones y sus eventos se conservan en Supabase.
- El schema expone `typeDefinitions` y metadata de presentación.
- El endpoint MCP Streamable HTTP y su OAuth forman parte del servicio desplegado.

No se reclasificaron automáticamente Objetos históricos como Sources. La decisión requiere contexto editorial.

## Compatibilidad temporal

- El schema conserva `presets` y `legacyPresets`.
- v4.1 escribe mediante `fields`.
- Los valores pueden reflejarse en `details` para clientes anteriores.
- La lectura puede inferir claves conocidas desde `details`.
- Un valor histórico incompatible aparece con un estado legacy.
- `Post` y `Snippet` conservan su valor físico en `tipo`.

| Entrada legacy | Resultado actual |
| --- | --- |
| `Concepto` | `Historia` |
| `Documento` | `Objeto` |
| `Evidencia` | `Objeto` |
| `Biblioteca` | `Historia` |
| `Fuente` | `Source` |

## Reglas para clientes

1. Indexa campos por `field_key`.
2. Consume las cuatro listas de tipos por separado.
3. Construye formularios desde `presetDefinitions` y `fields`.
4. Resuelve antes de crear campos personales.
5. Valida antes de guardar.
6. Lee `resolved_fields`.
7. Retira `flag` de UI, payloads y fallbacks.
8. Presenta Source y Simulacion con sus componentes diferenciados.
9. No muestres UUIDs crudos: resuelve referencias a nombres y vistas previas.

<Warning>
  Los clientes que todavía muestran nueve “ítems canónicos” mezclando Post y Snippet están usando el contrato anterior.
</Warning>
